01 Overview

How OD builds an agentic platform

Open Design's most important architectural decision: don't build a new AI agent. Delegate the entire agent loop — model calls, tool use, context management, permission handling — to the user's existing coding agent CLI. OD's job is to detect it, compose a skill-aware prompt, feed it a working directory, and stream its output to a sandboxed preview.

Architecture in one line: Browser ↔ Daemon (:7456) ↔ Agent CLI + Filesystem. All state that matters is files. 
── System overview ─────────────────────────────────────────

  Browser (Next.js 16)
    ↕ SSE / WebSocket
  od daemon (Node.js, port :7456)
    ├── Session manager     (1 per browser tab)
    ├── Skill registry      (scans 3 locations, hot-reloads)
    ├── Design-sys resolver (loads DESIGN.md, injects into prompt)
    ├── Agent adapter pool  (one adapter per detected CLI)
    ├── Artifact store      (plain files → ./.od/)
    └── Export pipeline     (HTML / PDF / PPTX / ZIP)
    ↕ spawn + stdout
  Agent CLI (claude / codex / gemini / cursor-agent / …)
    ↕ file system
  ./.od/artifacts/<slug>/ (real on-disk project folder)
02 Deployment

Three deployment topologies

The same web bundle runs in three shapes depending on which transports are enabled:

Topology A
Default
Fully local. Browser → Next.js (:3000) → od daemon (:7456) → spawns agent CLIs. One pnpm tools-dev run web starts everything. Zero config, no accounts. All secrets stay on your machine.
Topology B
Advanced
Web on Vercel + daemon tunneled. Run od daemon --expose, which prints a cloudflared tunnel URL. Paste into the deployed app's "Connect daemon" screen. Daemon holds all secrets. Vercel holds nothing sensitive.
Topology C
Limited
Vercel + direct API (no daemon). Browser → Vercel serverless → Anthropic Messages API. BYOK stored in localStorage (with explicit warning). No local CLI, no filesystem artifacts (IndexedDB only), no PPTX export. The "just try it" path.
03 Components

Logical component map

Web App — 4 panes

💬 Chat pane

Free-text prompt input. Shows streaming tool-call feed and agent text output as it arrives via SSE. First pane to appear — time to first byte is the discovery form.

🌳 Artifact tree

Live file-system view of the artifact directory. Updates in real time as the agent writes files. Every file is clickable — opens in an editor pane.

🖼️ Preview iframe

Sandboxed <iframe sandbox="allow-scripts">. Never allow-same-origin. Hot-reloads as files write. Loads index.html when the agent signals completion.

💡 Comment/slider overlay

Activates after preview loads. Click captures [data-od-id] from the iframe DOM → surgical edit instruction back to the agent. Sliders re-send parameterized prompts.

Why Next.js instead of a Vite SPA? SSR for the marketing landing page + serverless routes for Topology C's direct-API path + Vercel as a first-class deployment target. A plain SPA would need a separate server for all three.
04 Daemon

The daemon — heart of the backend

The daemon is a long-running Node.js/Express process distributed as a single binary (via pkg) or a thin npm script. It listens on http://localhost:7456 and is the only process that touches the filesystem, spawns agents, and holds session state.

Session lifecycle

1

Session created

Browser opens a new tab → daemon creates a session object holding active agent handle, skill reference, design-system body (cached), last artifact ID, and in-flight tool-call state.

2

Prompt assembly

BASE_SYSTEM_PROMPT + DESIGN.md body + SKILL.md body composed in order. Cached per session after first fetch — zero latency on subsequent sends with the same skill/system combo.

3

Agent invocation

Adapter spawns the CLI with CWD = new artifact directory. The agent has a real filesystem to write into. stdout is parsed as JSON Lines (if supported) or line-by-line.

4

Stream routing

Agent events classified as tool_call, text_delta, or thinking. Streamed back to the browser via SSE. Artifact tree updates live as files materialize.

5

Completion + persistence

Agent signals done. Daemon appends to history.jsonl: { ts, sessionId, artifactId, action, skill, promptHash }. Preview iframe loads the primary output file.

GC

Session garbage-collected (24h)

Sessions are ephemeral. Artifacts under ./.od/artifacts/ are never deleted automatically — they persist forever until the user removes them.

05 Agent adapters

The agent adapter pool

Each adapter implements a 4-step interface: detect → spawn → stream → report capabilities. OD maintains one adapter instance per detected CLI and reuses it across sessions.

Adapter interface

// Simplified TypeScript interface
interface AgentAdapter {
  detect(): Promise<boolean>;          // PATH lookup + config-dir probe
  spawn(opts: {
    systemPrompt: string;
    userPrompt: string;
    cwd: string;                         // artifact directory
  }): AsyncIterable<AgentEvent>;
  capabilities: {
    multiTurn: boolean;
    surgicalEdit: boolean;               // required for comment mode
    nativeSkills: boolean;               // reads SKILL.md natively
    toolUse: 'full' | 'minimal' | 'none';
  };
}

06 Prompt engine

The 3-layer prompt stack

Every generation composes a system prompt from three layers in order. The agent sees them as a single concatenated string (for CLI agents) or a structured system parameter (for API mode).

Layer 1
Base system
Output contract + designer persona.
"You are an expert designer working with the user as your manager. You produce design artifacts in HTML. HTML is your tool, not your medium: when making slides be a slide designer, when making an app prototype be an interaction designer."

Key constraints: wrap every deliverable in <artifact>, no markdown code fences, emit a discovery form on turn 1 before doing anything else.
Layer 2
DESIGN.md
Visual identity injection.
The full 9-section brand doc: palette (OKLch values), font stack, spacing scale, component patterns, motion easing, voice. Injected as a prefix before every run.

Skills can declare od.design_system.sections: [color, typography] to prune to only the relevant sections — saves tokens, reduces noise.
Layer 3
SKILL.md
Workflow rules + output spec.
The skill's Markdown body: what steps to follow, what reference files to read first (pre-flight enforced), what quality checklist to run, what the primary output file should be named, and any OD extension declarations.

Swapping the skill in the top bar → next send uses the new skill body. Cached in-memory per session after first fetch.

Prompt composition code

// Pseudo-code: daemon prompt assembly
function composePrompt(session: Session): string {
  return [
    BASE_SYSTEM_PROMPT,
    session.designSystem.body,   // DESIGN.md — cached after first load
    session.skill.body,          // SKILL.md — cached after first load
  ].join('\n\n---\n\n');
}

// For CLI agents: fold system into user message
const userMsg = `[System context]\n${composePrompt(session)}\n\n[Task]\n${userPrompt}`;

// For API fallback: use proper system parameter
const apiReq = { system: composePrompt(session), messages: [{ role: 'user', content: userPrompt }] };
07 Discovery prompt

The discovery prompt — turn 1 is sacred

The src/prompts/discovery.ts file is the most important code in the system. It stacks before the official OD designer prompt, so its 3 hard rules beat everything else.

Rule 1 — Turn 1: emit discovery form, nothing else

First output is one short prose line + a <question-form id="discovery"> block. No file reads, no Bash, no TodoWrite, no extended thinking. This is the "time to first byte" — the form appears in under a second. Questions: output type, platform surface, audience, visual tone (up to 2), brand context.

Rule 2 — Turn 2: branch on brand answer

If user says "pick a direction for me" → emit <question-form id="direction"> with 5 curated visual directions (each with a specific OKLch palette, font pairing, layout posture cue). If user provides brand spec/URL → extract brand tokens via Bash+Read, then TodoWrite. Otherwise → TodoWrite directly.

Rule 3 — Turn 3+: work the plan

TodoWrite plan streams live. Agent must read all skill reference files first (pre-flight enforced by SKILL.md). Builds artifact on disk. Runs 5-dimensional self-critique gate (Philosophy · Hierarchy · Execution · Specificity · Restraint). Emits <artifact>. Preview loads.

The 5-dimensional critique gate

DimensionQuestion askedAnti-pattern caught
PhilosophyDoes this have a coherent aesthetic point of view?Generic "AI-looking" output with no identity
HierarchyIs information structured for clarity and guided reading?Everything the same visual weight
ExecutionAre technical decisions correct? Code clean?Broken CSS, misused components
SpecificityIs it specific to this brief, or generic?Lorem ipsum, placeholder copy, generic hero images
RestraintDoes it avoid over-design and clutter?Too many colors, excessive animation, noisy layout
08 Preview

Sandboxed preview renderer

The preview iframe is always <iframe sandbox="allow-scripts"> — never allow-same-origin. Artifact code has zero access to window, cookies, or parent DOM.

Artifact typeRender strategy
Static HTMLsrcdoc load with all CSS inlined. No external requests. Works offline.
JSXBootstrap injects vendored React 18 + Babel standalone, then dynamically evals the JSX. Follows Open CoDesign's approach.
MarkdownRendered via lightweight Markdown parser, styled with active design system typography tokens.
PPTX previewRendered as a horizontal-swipe HTML deck derived from slides.json — not the actual .pptx binary.

The preview hot-reloads as the agent streams file writes, debounced at 100ms. The slider UI (when skills declare od.parameters) re-sends parameterized prompts without round-tripping the full chat context — extremely fast for small aesthetic adjustments.

09 Artifact store

The artifact store — plain files by design

# Every generation creates this structure:
./.od/
├── config.json                         # project-level daemon config
├── artifacts/
│   ├── 2026-04-24T10-03-12-landing/
│   │   ├── artifact.json               # skill, promptHash, parent, mode
│   │   ├── index.html                  # primary output
│   │   └── assets/                     # skill-generated images, fonts
│   └── 2026-04-24T11-22-05-dashboard/
│       └── ...
├── history.jsonl                       # append-only action log
└── sessions/
    └── <session-id>.json              # ephemeral, GC'd after 24h

Design rationale

Plain files → git-friendly

git add ./.od/artifacts/ and review design history in pull requests. No database dump, no binary blob, no vendor tooling required.

artifact.json → reconstructable

OD can rebuild the full artifact tree from metadata alone — no database needed. Records the exact skill, design system, and prompt hash used.

history.jsonl not SQLite

Append-only, greppable, diff-friendly. A deliberate choice against Open CoDesign's SQLite approach — filesystem is the database.

Sessions separate from artifacts

Sessions are ephemeral UI state (24h GC). Artifacts are durable permanent records — never auto-deleted.

11 Data flow

Complete request lifecycle

1

User sends prompt

Web sends { method: "session.generate", sessionId, prompt, modeHint } via WebSocket.

2

Daemon assembles prompt

Picks active skill + loads DESIGN.md. Materializes new artifact dir ./.od/artifacts/<slug>/. Composes 3-layer system prompt.

3

Agent adapter invoked

Spawns CLI with system prompt, user prompt, and CWD = artifact directory. Agent has real filesystem access.

4

Events stream to browser

tool_call events (file writes), text_delta (agent thoughts), thinking blocks stream to chat pane and artifact tree in real time.

5

Preview loads

Agent signals done. Primary output file loads in sandboxed iframe. Comment + slider overlay activates.

6

History appended

{ ts, sessionId, artifactId, action: "generate", skill, promptHash } appended to history.jsonl.

+

Comment → surgical edit

User clicks element → popover note → web sends { artifactId, elementId, note }. Daemon re-invokes agent with targeted edit instruction. Only that element is modified.
